## 1. 회로도 분석

### 1-1. IC1(NUC029) 핀 매핑 확인

| 핀 | 신호 | 연결 |
|---|---|---|
| 19 | P2.0 | R21(1K) → Q21(MMBT2222A) 베이스 → 컬렉터 = **OUT1** 넷 (CN4A 20번, FPC 커넥터) |
| 20 | P2.1 | R22(1K) → Q22(MMBT2222A) 베이스 → 컬렉터 = **OUT2** 넷 (CN4A 21번) |
| 45 | P1.2/AIN2 | R3(100K) 거쳐 **ADC_IN** 넷 = U81(MCP73831 배터리 충전 IC) 3번핀(VBAT 출력) — 배터리 전압 센싱 |
| 43 | P1.0/AIN0 | **TOUCH_ADC** 넷 직결 (아래 1-2 참조) |
| 41 | VDD | FB1(페라이트비드) ← 5V, 디커플링 C2(104p)+C3(10uF) |
| 42 | AVDD | FB2(페라이트비드) ← 5V, 디커플링 C1(104p) |

**결론**: P2.0/P2.1(OUT1/OUT2 드라이버)과 P1.2(ADC_IN/배터리전압)는 회로도상 **완전히 분리된 별개 넷** — 직접적 전기 연결 없음. 다만 둘 다 같은 **5V 레일**(U5 FP6715S6CTR 부스트 컨버터 출력)을 공유하므로, OUT1/OUT2 구동 시 부하 전류로 5V가 순간적으로 처지면 VDD/AVDD/TOUCH_ADC 풀업 기준전압도 간접적으로 같이 흔들릴 수 있음.

### 1-2. TOUCH_ADC 회로 (P1.0)

```
5V ── R13(8.2M) ── 노드A(TOUCH 패드) ── R12(10K) ── 노드B ── R11(1K) ── TOUCH_ADC(→P1.0)
                                              │
                                            DZ11(BZT52C5V1, 5.1V 제너) ── GND
```

- 이상적(DC 정상상태, 무부하)으로는 미터치 시 **거의 5V**가 측정되어야 함 (R13~R11 경로에 흐르는 전류는 ADC 입력 누설전류 + DZ11 역방향 누설전류뿐, nA급 → IR강하 무시 가능).
- **실측 시 전압이 크게 낮게 나오는 이유(스코프/DMM 프로브 사용 시)**: R13이 8.2MΩ로 매우 높아, 프로브 입력임피던스(1X≈1MΩ, 10X≈10MΩ)가 분압을 만들어버림 (10X 기준 예상치 ≈2.7V, 1X 기준 ≈0.54V). → **회로 결함이 아니라 측정 부하(loading) 아티팩트**.
- **추가 원인(프로브 없이도 발생 가능)**: R13~R11 총 저항(~8.21MΩ)과 ADC 핀/PCB 기생 커패시턴스(수~수십 pF)로 인한 RC 시정수가 커서(τ≈100µs 이상), MCU ADC의 짧은 샘플링 타임 내에 S/H 커패시터가 충분히 충전되지 못해 **실제 DC 전압보다 낮게 변환**될 수 있음.
- **테스트 방향(논의됨)**: R13을 8.2M→더 낮은 값(예: 1M/470K/100K)으로 바꾸면 프로브 부하·ADC 정착시간 문제는 완화되나, 터치 감도(패드 절연층 위에서의 간접 터치 감지력)와 트레이드오프 있음 — `TOUCH_BEFORE_AFTER.md`에 R13 4.1MΩ(8.2M×2 병렬) 실측 결과 있음, DZ11 누설전류가 비선형적으로 같이 늘어나 수확체감 확인됨.

### 1-3. P99 디버그/ISP 커넥터 (1.27mm, 5핀)

| 핀 | 신호 |
|---|---|
| 1 | RST |
| 2 | ICSPCLK |
| **3** | **5V** (보드 5V 레일에 직결) |
| 4 | ICSPDAT |

→ P99-3에 디버그용 5V 인가 자체는 원래 용도(ISP 툴 전원 공급 핀)라 문제없음. 단, **배터리/USB로 보드 자체 5V(U5 부스트 출력)가 이미 살아있는 상태에서 동시 인가는 지양** — 두 전원 경합 가능. 전류제한(수백 mA) 설정 권장.

## 2. `task_MotorCtrl()` 코드 검토 및 수정 ([main.c:1716](../main.c#L1716))

### 2-1. 오늘 발견/수정한 버그

| # | 문제 | 수정 |
|---|---|---|
| ① | `rTouchChattering` 정적 초기값 **15** vs 윈도우-리셋값 **25** 불일치 → 파워온 직후 첫 50ms 윈도우에서 터치 중이면 unsigned underflow로 ON 판정 영구 누락 (엣지케이스) | 초기값을 **25**로 통일 |
| ② | ON 판정 조건이 `== 20`(정확히 일치해야만 트리거, 5샘플/≈5ms 만에 확정 — 노이즈에 취약) | **`<= 10`**로 변경 (15샘플/≈15ms 필요, OFF쪽 26샘플과의 비대칭 완화) |
| ③ | `rPowerOnCnt` 감소 블록이 함수 내에 **완전히 동일하게 2번** 중복 (1731줄 + 구1780줄) → 1ms마다 2씩 감소 → 파워온 후 모터 잠금 시간이 의도한 500ms의 **절반(≈250ms)**으로 단축 | 중복 블록 제거, 1회만 감소하도록 수정 → **500ms 복원** |
| ④ | 주석과 실제 값 불일치: `TOUCH_CHECK_WINDOW_MS`(실제 50) vs 주석("25ms/1000ms")×3곳, 임계전압 주석("2V"/"0.5V") vs 실제(2.5V) | 주석을 실제 값 기준으로 전부 정리 |

### 2-2. 현재 로직 요약 (수정 후)

```c
#define TOUCH_CHECK_PERIOD_MS  1000
#define TOUCH_CHECK_WINDOW_MS  50

// rTouchChattering 초기/리셋값 = 25
// Not Connect(미터치, ADC > 2.5V 상당): ++rTouchChattering > 50  → 26샘플(≈26ms) 연속 시 F_MOTOR_ON=FALSE
// Connect(터치, ADC <= 2.5V 상당)    : --rTouchChattering <= 10  → 15샘플(≈15ms) 연속 시 F_MOTOR_ON=TRUE
// 윈도우 밖(950/1000ms): 매 ms rTouchChattering=25, rTouchAlready=FALSE 로 강제 리셋
// rPowerOnCnt(500): 파워온 후 500ms 동안 rInterupt_MotorStatus=FALSE 유지 (모터 강제 OFF)
```

- 임계값(2.5V, 미터치/터치 구분 방향)은 하드웨어 TOUCH_ADC 회로(1-2)와 일치 — 미터치 시 High(5V쪽), 터치 시 Low(GND쪽) 풀다운.
- 다만 1-2에서 확인한 **8.2MΩ 고임피던스 노드의 신호 불안정성**(측정 부하, ADC 정착시간, 20Hz 모터 스위칭 노이즈 커플링 — `TOUCH_REVIEW.md` §4 참조)이 남아있는 한, 소프트웨어 디바운스만으로는 오판정 여지가 있음. `TOUCH_BEFORE_AFTER.md`의 다음 단계(R13 추가 하향, DZ11 교체, 20Hz 노이즈용 병렬 커패시터)가 근본 해결책으로 여전히 유효.

## 3. 파워온 → main loop 진입 전 모터 OFF 검증

`main()` 시작(1319줄, `MOTOR_OFF;` 최초 실행)부터 `while(1)` 진입(1550줄)까지 추적한 결과:

- `MOTOR_OFF` 3회 재확인(1319/1418/1481줄), `F_MOTOR_ON=FALSE` 2회(1327/1480줄), `rInterupt_MotorStatus=FALSE`(1421줄)가 **TIMER1 시작(1425줄) 이전**에 세팅되어 있어, 모터를 실제 구동하는 `TMR1_IRQHandler`(598-609줄)가 인터럽트 활성화 직후 곧바로 걸리더라도 항상 `MOTOR_OFF; return;`으로 안전하게 처리됨.
- `task_MotorCtrl()`(터치 판정 → F_MOTOR_ON 변경 가능 지점)은 `while(1)` 루프 안(1557줄)에서만 호출되므로 루프 진입 전에는 절대 실행되지 않음.
- **결론: main loop 진입 전까지, 그리고 진입 후 추가 500ms(rPowerOnCnt, §2-1 ③ 수정으로 정상화)까지 모터는 어떤 코드/인터럽트 경로로도 켜질 수 없음 — 검증 완료.**
- 유일한 비제어 구간은 MCU 리셋 직후~`main()` 첫 명령 실행 전(수 µs, 리셋 디폴트 Quasi-bidirectional 약한 풀업) — 펌웨어로 제어 불가하나 구동력이 무시할 수준이라 실질적 영향 없음.
